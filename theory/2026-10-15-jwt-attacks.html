JWT Attacks

2026-10-15 · 9 min read

JSON Web Tokens are the default session and authorisation token for modern APIs and single-page apps. A JWT is a signed claim the client carries and the server trusts, which makes the server's verification logic the target. Most JWT vulnerabilities are failures to verify the signature correctly, and they lead straight to authentication bypass and privilege escalation.

Anatomy

Three base64url parts separated by dots: header.payload.signature. Decode them with any tool:

# header   {"alg":"HS256","typ":"JWT"}
# payload  {"sub":"alice","role":"user","exp":1735689600}
# signature  HMAC/RSA over  base64url(header) + "." + base64url(payload)

echo <token> | cut -d. -f1 | base64 -d 2>/dev/null   # read the header
jwt_tool <token>                                       # inspect + attack toolkit

The entire model rests on the server recomputing and checking that signature before trusting any claim.

The classic failures

FlawMechanismResult
alg:noneServer accepts an unsigned tokenForge any claims
Signature not checkedApp decodes but never verifiesTamper freely
Weak HMAC secretSymmetric key is crackable offlineMint valid tokens
RS256 → HS256 confusionServer verifies an HS256 token using the RSA public key as the HMAC secretForge with a public key
jku/kid abuseAttacker controls where the verify key is fetched, or injects via kidVerify with an attacker key

Worked examples

# alg:none — strip the signature, set alg to none, flip a claim
jwt_tool <token> -X a                              # automated "none" attack
# → header {"alg":"none"},  payload role=admin,  empty signature

# weak HMAC secret — crack it offline, then sign your own token
hashcat -m 16500 token.txt /usr/share/wordlists/rockyou.txt
jwt_tool <token> -S hs256 -p 'cracked-secret' -I -pc role -pv admin

# RS256 → HS256 confusion — sign with the server's PUBLIC key as the HMAC key
jwt_tool <token> -X k -pk public.pem

The alg:none and algorithm-confusion attacks share one root cause: the server lets the token dictate how it is verified. The fix is that the server pins the expected algorithm and key and ignores the header's claims about them.

What attackers change

Once verification is defeated, the valuable claims are identity and authority — flip role: user to role: admin, change sub to another user, or extend exp. Because JWTs are usually stateless, a forged token cannot easily be revoked mid-life.

Prevention

  • Pin the algorithm server-side; never honour alg:none; do not let a token switch asymmetric↔symmetric.
  • Use long, random, rotated keys; validate kid/jku against an allow-list — never fetch keys from attacker-controlled URLs.
  • Validate every claim — exp, aud, iss — on each request.
  • For sensitive apps, keep a server-side session or revocation list so a leaked token can be killed.
  • Detect tokens with none/unexpected algorithms and signature-verification failures.
