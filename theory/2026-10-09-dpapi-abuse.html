DPAPI Abuse

2026-10-09 · 9 min read

The Data Protection API (DPAPI) is how Windows encrypts a user's secrets at rest — browser passwords and cookies, saved RDP and Wi-Fi credentials, the Windows Credential Vault, and many applications' stored secrets. It is convenient and transparent, which also makes it a rich target: once you can act as a user (or own the domain), DPAPI is the key that unlocks a pile of their saved credentials.

What DPAPI protects

  • Browser secrets — saved passwords and cookies (session cookies are especially valuable, since they bypass MFA when replayed).
  • Windows Credential Manager / Vault — saved RDP, network share and application credentials.
  • Wi-Fi keys, scheduled-task creds, and many app secrets that call the DPAPI functions.

How it works (the part that matters)

Each protected blob is encrypted with a key derived from a per-user master key, which in turn is protected by the user's password (and a machine key for machine-scoped data). So decrypting a blob needs the right master key, and the master key needs either the user's password, their password hash, or — the important part — the domain DPAPI backup key.

The domain backup key is the master skeleton: every domain controller holds a backup key that can decrypt any domain user's DPAPI master keys. An attacker who owns the domain can therefore decrypt the saved secrets of every user in it — which is why DPAPI is both a local-user and a domain-wide credential-access technique.

The access paths

You haveYou can decrypt
The user's password or NT hashThat user's master keys → their DPAPI blobs
Code running as the userTheir blobs transparently (the OS does the work)
Local admin / SYSTEM on the hostThe machine master key → machine-scoped secrets
The domain DPAPI backup key (domain owned)Any domain user's master keys → everyone's blobs

Why it is high value

DPAPI loot is often credentials the victim actively uses — a saved admin password in Credential Manager, a browser-stored password for an internal app, or a live session cookie that skips authentication entirely. It frequently yields lateral-movement and privilege-escalation material that never appeared in LSASS, and it works offline from copied blobs and master keys.

Detection & hardening

  • Monitor access to the DPAPI master-key directories and the Credential Vault, and alert on extraction of the domain backup key from a DC.
  • Prefer not storing credentials in browsers/Credential Manager for privileged accounts; use a managed secrets vault instead.
  • Short session-cookie lifetimes and token-binding reduce the value of stolen cookies (ties into the AiTM problem in the workflow).
  • Treat the domain backup key as crown-jewel material — its compromise means every user's saved secrets are exposed, a recovery consideration alongside AD persistence.
