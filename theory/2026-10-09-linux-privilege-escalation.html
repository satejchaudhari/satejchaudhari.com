Linux Privilege Escalation

2026-10-09 · 12 min read

You have a shell on a Linux host as a low-privileged user. Local privilege escalation is the step from that foothold to root, and on Linux it is almost always a misconfiguration rather than a memory-corruption exploit: a binary that runs with privileges it should not, a writable file the system trusts, or a permission a group quietly grants. This page is the operator's map of those classes and how each is abused and found.

Enumerate first — let a tool do the sweep

Never escalate blind. Run an automated enumeration script, read its output, and only then reach for a technique. The classics: 

# the standard automated sweeps
./linpeas.sh                 # LinPEAS — colour-coded, finds nearly everything
./lse.sh -l1                 # linux-smart-enumeration, levelled output
# manual quick wins
id; sudo -l                  # my groups, and what I can run as root
uname -a; cat /etc/os-release  # kernel / distro for exploit matching
find / -perm -4000 -type f 2>/dev/null   # SUID binaries
The order that pays off: sudo -l → SUID → cron → writable files → capabilities → group memberships → kernel. Quiet, config-based wins come before loud kernel exploits that can panic the box.

SUID / SGID binaries

A SUID binary runs with its owner's privileges regardless of who launches it; SUID-root therefore runs as root. The exploit is to find a SUID binary that can be made to execute your commands, read protected files, or write where it should not. GTFOBins is the canonical lookup — it lists, per binary, the exact invocation that breaks out. 

find / -perm -4000 -type f 2>/dev/null
# example: a SUID find breaks straight to a root shell
find . -exec /bin/sh -p \; -quit
# custom SUID binary calling a command by relative name -> PATH hijack (below)

Sudo rules

sudo -l lists what your user may run as another user — the single highest-value check. A rule that lets you run almost any interpreter, editor, or GTFOBins-listed binary as root is a direct escalation; so are classic sudo CVEs and environment tricks.

Cron jobs & systemd timers

Scheduled tasks run as their owner, usually root, on a timer. If you can influence what a root cron runs — a writable script, a writable directory in its path, or a wildcard it expands — you execute as root at the next tick. 

cat /etc/crontab; ls -la /etc/cron.*; systemctl list-timers
# writable script run by root cron -> append your payload
echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' >> /path/backup.sh
# wildcard injection: a root cron doing `tar czf backup.tar.gz *` in a writable dir
echo 'mypayload' > '--checkpoint=1'; echo 'mypayload' > '--checkpoint-action=exec=sh payload.sh'

PATH & wildcard injection

A privileged program that calls another command by its name rather than its absolute path trusts $PATH. If you control a directory earlier in PATH (or the program's working directory), drop a malicious binary of that name. Wildcard injection is the same idea for shell globs — crafted filenames become command-line arguments.

Linux capabilities

Capabilities slice root's power into units, and a binary granted a dangerous one escalates without being SUID. cap_setuid lets a binary set its UID to 0; cap_dac_read_search reads any file; others allow module loading or raw sockets. 

getcap -r / 2>/dev/null
# python with cap_setuid -> set uid 0 and drop a root shell
./python -c 'import os; os.setuid(0); os.system("/bin/sh")'

Writable sensitive files

  • Writable /etc/passwd — add a root-UID user with a known password hash (or remove the x to blank root's password).
  • Writable /etc/shadow — replace root's hash with one you know.
  • Writable service unit / init script — edit the ExecStart a root service runs, then restart it or wait for a reboot.
  • Readable backups / config / history — passwords in .bash_history, .env, config files, and world-readable backups.

Group memberships & container escapes

  • docker group — equivalent to root: run a container that bind-mounts / and chroot into it.
  • lxd / lxc group — launch a privileged container mounting the host disk.
  • disk group — read/write raw devices with debugfs to pull /etc/shadow.
  • NFS no_root_squash — mount the export, drop a root-owned SUID binary from a box you control.

Kernel & the last resort

A kernel or privileged-service exploit (Dirty COW, Dirty Pipe, PwnKit/ pkexec, OverlayFS, Sudo Baron Samedit) matches a specific version — confirm uname -a and the package version before running anything, because a wrong kernel exploit panics the host. Prefer the config wins above; use an exploit only when enumeration comes up dry.

Detection & hardening

  • Minimise SUID/SGID and capabilities; audit them (find -perm, getcap) and alert on new ones.
  • Tightly scope sudo rules; never allow interpreters/editors, drop env_keep, keep sudo patched.
  • Make cron scripts and their directories root-owned and non-writable; avoid wildcards on untrusted input.
  • Monitor with auditd (execve, setuid, writes to /etc/passwd/shadow) and ship it off-host — see the Logging page.
  • Keep users out of the docker/lxd/disk groups unless they truly need root-equivalent access.
