Modern AMSI Bypasses — Why They Still Work

2026-10-08 · 9 min read

The Antimalware Scan Interface (AMSI) is the hook that lets Windows hand a script or a block of .NET code to the installed antivirus to be checked at the moment it is about to run — defeating the old trick of never writing anything to disk. It is genuinely useful, and yet bypasses for it keep appearing and keep working on fully-patched, EDR-protected machines. This page is about why that is, explained at the level of the idea rather than the implementation. The goal here is to understand the shape of the problem; it deliberately skips exact instructions, offsets and register-level detail, because the point is the concept, not a recipe. For where AMSI sits among the other evasion surfaces, see Windows Defense Evasion.

The flaw is structural, not a bug

The reason AMSI can be bypassed at all is not a coding mistake Microsoft will one day fix — it is where the check lives. When PowerShell or the .NET runtime scans a piece of content, the scan happens inside the very process that is running the attacker's code. The runtime calls a function, the function asks the antivirus "is this clean?", and the runtime trusts the answer. Everything in that sentence — the function, the answer, the little bit of state that remembers whether AMSI is even available — sits in the same process, on the same side of the trust boundary as the code being inspected.

A security check that runs in the same place as the thing it is checking can always be influenced by that thing. Every AMSI bypass is a different way of doing exactly that — and because the flaw is structural, closing one route does not close the category.

So the useful mental model is not "find the hole in AMSI" but "make the in-process check come back clean." There are three broad ways to do that, and they are worth seeing as an evolution — each generation is an answer to how the previous one got caught.

Family 1 — Tell the runtime AMSI isn't working

The gentlest approach does not fight the scanner at all; it convinces the runtime there is nothing to call. The scripting engine keeps a small internal flag that effectively means "AMSI failed to start up." It checks that flag before every scan, and if it is set, it simply skips the scan — sensible fail-open behaviour so that a broken antivirus does not break PowerShell. Flip that flag and the engine politely stops scanning anything, for the rest of the session.

Why it works in a modern environment: it never touches antivirus code or looks like memory tampering — it uses the runtime's own legitimate features to change a value the runtime put there itself. The important nuance is that this state is fragile: it may not exist yet when the process first starts, and an EDR may reset it. That is why real tooling re-asserts it continually — before each command, each script, each cycle of a loader — rather than once. The lesson is that this is a piece of state to be kept flipped, not a one-time switch.

Family 2 — Overwrite the scan function (and why it now gets caught)

The classic approach is blunter: reach into the AMSI library in memory and overwrite the start of the scan function so that it always reports "clean" and never actually consults the antivirus. For years this was the default, and it still works where nothing is watching.

But this is exactly where modern defence caught up. Overwriting the function leaves evidence: the code in memory no longer matches the code Microsoft shipped on disk. EDRs learned to take the well-known scan functions and compare what is loaded in the process against a known-good copy; any difference is a loud, high-confidence signal of tampering. Patching the function went from "reliable" to "reliably detected," which is the pressure that produced the next generation.

Family 3 — Patchless: change the outcome, not the code

The current favourite avoids modifying the scan function entirely, so there is nothing for a byte-comparison to find. Instead of rewriting the code, it uses the CPU's built-in debugging facility to pause execution at the instant the scan function is about to run, and a small custom exception handler the process registers for itself quietly makes that paused call "return clean" and resumes. The library's bytes are never altered — hence "patchless" — so an integrity check comparing memory to disk sees nothing wrong.

A few conceptual points explain why it is effective, without needing any low-level detail:

  • It defeats the detection that killed Family 2. The tampering has moved out of the program's code — which is easy to verify — and into fleeting, per-execution CPU and handler state, which a static code scan does not look at.
  • It has to cover every path the scan can run on. The CPU's pause-points are set per execution thread, and a scripting engine may run its work on several threads, so the technique must apply itself to all of them or a scan slips through on an uncovered one.
  • Order matters. The handler that fakes the result must be in place before the pause-point is ever armed — otherwise there is a window where execution stops and nothing is there to handle it, which crashes the process and is itself a glaring signal.

Why this keeps working in modern environments

Put the three families side by side and the pattern is clear. Each new defensive capability — content scanning, then in-memory integrity checking — was answered not by defeating it head-on but by moving the tampering somewhere the new detection does not look: from the antivirus engine, to a managed flag, to the function's bytes, to volatile per-thread state. The attacker keeps winning the same structural argument: the check and the code share one process, so whatever the defender can see from inside that process, the attacker can reach too.

This is why AMSI bypass is best understood as an arms race over visibility, not a single vulnerability. The durable answer is not a better in-process check — it is a vantage point outside the process.

What actually catches it

Because every one of these tricks lives inside the process, the defences that work are the ones that watch from outside it:

  • Kernel and hardware-assisted telemetry (ETW "threat-intelligence" events and EDR sensors) can observe the suspicious setup these techniques require, where an in-process scan cannot.
  • AMSI's own tamper signals and memory scanning — modern AMSI reports when its state looks manipulated, and EDRs periodically scan loaded modules for the integrity mismatches and known bypass patterns Family 2 leaves behind.
  • Looking at the right state for Family 3 — an ordinary, non-debugged process that has debugging pause-points set on security functions, or that has just wired up its own exception handler around them, is anomalous and detectable even though no code was changed.
  • Breadth over any single control — AMSI is one signal among many. Script-block and module logging, on-host behavioural rules, and newer PowerShell hardening mean that silencing AMSI alone no longer makes activity invisible. See Windows Telemetry & PowerShell Logging.

The takeaway mirrors the rest of the evasion material on this site: a control that lives in the same trust boundary as the attacker's code can always be influenced by it, so the real defensive investment is in cross-surface, outside-the-process visibility that a bypass cannot reach.
