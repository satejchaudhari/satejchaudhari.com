Linux Persistence

2026-10-09 · 9 min read

Linux persistence follows the same logic as Windows through Unix mechanisms: anything that runs code on a schedule, at login, or when a trusted binary loads is a candidate. The operator chooses by the privilege held and the noise it makes; the defender treats this as the list of places to baseline and monitor. The mechanisms, by trigger:

Scheduled execution

MechanismWhere it lives
cronUser crontabs, /etc/crontab, /etc/cron.d and the cron.{hourly,daily,...} directories.
systemd units & timersService units plus .timer units (and user-level units under ~/.config/systemd) — the modern equivalent of cron.
at / anacronOne-shot and catch-up scheduling, easy to overlook.

Login & shell triggers

  • SSH authorized_keys — an attacker public key in a user's (or root's) file is the most common and reliable Linux re-entry.
  • Shell init files — ~/.bashrc, ~/.profile, /etc/profile.d/ run on each interactive login.
  • rc / init scripts — legacy /etc/rc.local and init scripts that run at boot.

Hijacks that ride trusted loads

  • LD_PRELOAD / /etc/ld.so.preload — a shared object loaded into processes, intercepting library calls (also a classic userland rootkit technique).
  • PAM modules — a tampered or added PAM module in the auth stack can accept a backdoor credential or log passwords.
  • SUID backdoor — a root-owned SUID binary left behind for instant re-escalation (overlaps with Linux privesc).
  • Loadable kernel modules — a malicious LKM for kernel-level hiding and persistence (the loudest and most capable, needs root).

Service & application-level

  • Web shells on an exposed app, and cron/webhook callbacks from the application tier.
  • New or trojaned service accounts, added SSH users, and container images baked with a backdoor.
  • Package / update hooks — post-install scripts that re-establish access.
As on Windows, reliability versus noise drives the choice: an SSH key is reliable and quiet; a kernel module is powerful but conspicuous. A careful operator also plants a second, different mechanism so losing one does not lose access.

Detection & hardening

  • Baseline and monitor cron/systemd units, authorized_keys, shell init files, ld.so.preload and the PAM stack; alert on changes with auditd (file watches + execve) shipped off-host — see Logging.
  • File-integrity monitoring (AIDE/Tripwire) over system binaries, PAM, and init paths.
  • Restrict who can write units and SSH keys; disable password auth where keys are used; sign and verify packages.
  • Hunt for new SUID binaries and unexpected kernel modules (lsmod, find -perm -4000).
