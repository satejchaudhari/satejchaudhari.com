Web API Fuzzing

2026-10-07 · 10 min read

Fuzzing a Web API is the same idea as fuzzing a website for hidden directories, but the target has a different shape. A web server hands a browser HTML, CSS and JavaScript to render; an API exists so one piece of software can talk to another, exchanging structured data — usually JSON or XML — and triggering actions. Nobody looks at an API in a browser, so the interesting surface is not hidden pages, it is undocumented endpoints and parameters. That changes what you fuzz for, and this page is about doing it properly.

The three API styles you will meet

Almost everything on the web falls into one of three models, and each one is discovered and fuzzed differently, so the first job on any target is to work out which one you are looking at.

REST

The common case. REST is resource-oriented: every resource has its own URL (the endpoint) and you act on it with ordinary HTTP verbs — GET to read, POST to create, PUT/PATCH to update, DELETE to remove. The paths are hierarchical and predictable: 

GET    /users          # a collection
GET    /users/123      # one user
GET    /products/456   # one product
DELETE /items/789      # remove an item

Parameters arrive in three places, and all three are worth fuzzing: query parameters after a ? (/users?limit=10&sort=name, used for filtering, sorting and pagination), path parameters baked into the URL (/products/{id}, identifying a resource), and body parameters sent inside a POST/ PUT/PATCH request as JSON.

SOAP

Older, heavier, still everywhere in enterprise systems. SOAP is XML-based and usually exposes a single endpoint; the operation you want is decided by the contents of the XML message, not by the URL. A SOAP request wraps its parameters in a <soapenv:Envelope>: 

<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:lib="http://example.com/library">
   <soapenv:Body>
      <lib:SearchBooks>
         <lib:keywords>cybersecurity</lib:keywords>
         <lib:author>Dan Kaminsky</lib:author>
      </lib:SearchBooks>
   </soapenv:Body>
</soapenv:Envelope>

The operations and their parameters are defined in a WSDL file — an XML description of the whole service. If you can read the WSDL you have the full map: every operation, every input and output, the data types, and the endpoint URL.

GraphQL

Modern and flexible. One endpoint (typically /graphql) serves everything, and the client asks for exactly the fields it wants in a query language — so there is no over-fetching and no under-fetching. Reads are queries, writes are mutations: 

query {
  user(id: 123) {
    name
    email
    posts(limit: 5) { title body }
  }
}

mutation {
  createPost(title: "New Post", body: "...") { id title }
}

API vs. web server — why the approach changes

The practical differences all point at the same conclusion: you fuzz an API for endpoints and parameters, not for files on disk.

 Web serverAPI
PurposeServe pages and content to a browserLet software exchange data and trigger actions
Data formatHTML, CSS, JavaScriptJSON, XML — per the API spec
Who uses itA human, directlyAnother program, on the user's behalf
ExposureUsually publicPublic, partner, or internal-only

Finding the endpoints and parameters

You cannot fuzz what you cannot see, so discovery comes first. Three sources recur across all three API styles, and you work down them in order of reliability.

  • Documentation and the schema. The quickest win. REST services often publish a machine-readable spec — Swagger / OpenAPI or RAML — frequently at /docs, /swagger.json or /openapi.json. SOAP hands you the WSDL. GraphQL exposes its entire schema through introspection: a single query returns every type, field, query and mutation, which GraphiQL and GraphQL Playground render for you.
  • Traffic analysis. When the docs are missing or incomplete, watch the real client. Burp Suite or the browser dev tools show every request a front-end makes — endpoints, parameter names, headers and body shapes — which is the ground truth of what the API actually accepts.
  • Fuzzing. What is left over. Even a documented spec rarely lists everything: there are endpoints omitted as "security through obscurity", internal-only functions, and routes still under development. A wordlist-driven fuzzer finds those, and the same technique finds undocumented parameters once you have an endpoint.
The documented spec is a starting point, never the whole picture. Assume there are endpoints and parameters it does not mention — those are usually the ones worth your time.

What "fuzzing an API" actually means

You send the API a stream of automated requests, each one a small mutation of a valid request, and watch for responses that stand out — a different status code, a different size, an error, a stack trace, a crash. Those deviations are where the bugs live. The mutations are things like:

  • injecting unexpected values into a parameter;
  • changing or adding request headers;
  • reordering or duplicating parameters;
  • sending the wrong data type, or malformed JSON/XML.

It matters because APIs have a large, often undocumented attack surface; because testing every input combination by hand is impossible; and because a fuzzer exercises the same malformed inputs a real attacker would, so you find the input-validation, injection and authorisation flaws before someone else does.

The three kinds of API fuzzing

  1. Parameter fuzzing. The core technique — hammer the values of query parameters, headers and body fields with unexpected or malicious input. This is how you surface injection (SQL, command), broken access control, and parameter tampering.
  2. Data-format fuzzing. Target the JSON or XML structure itself — break the nesting, flip types, abuse encoding and special characters. This finds parser bugs, resource exhaustion, and mishandling of malformed documents (XML parsers are a classic source of trouble here).
  3. Sequence fuzzing. APIs are stateful — endpoints depend on each other and order matters. Varying the order, timing and repetition of a chain of calls exposes race conditions, IDOR, and authorisation bypasses that no single request would reveal.

Discovering hidden endpoints in practice

Say a REST service documents five routes at /docs — read root, read/update/delete an item, create an item. Point a wordlist fuzzer at the base URL to find the ones it does not mention. With ffuf: 

# fuzz for undocumented endpoints under the API root
ffuf -u http://target.com/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/api/api-endpoints.txt \
  -mc 200,201,301,302,401,403,405

Read the status codes, not just the 200s. A 405 Method Not Allowed is a real endpoint that simply wants a different verb — try POST where a GET was rejected. A 401/403 is a route that exists but needs authentication. Anything returning 200 that is not in the docs is an undocumented endpoint worth probing by hand.

Once an endpoint is confirmed, fuzz its parameters the same way — a wordlist of likely parameter names against the endpoint, then a wordlist of values against a parameter you have confirmed. That second stage is where endpoint discovery turns into real findings: parameters that leak other users' objects (broken object-level authorisation), functions you should not be able to call (broken function-level authorisation), or values the server fetches on your behalf (SSRF).
