Payload & Maldoc Tradecraft

2026-10-15 · 10 min read

Once a lure is clicked or an attachment opened, something has to run and call home. "Maldoc tradecraft" is the craft of getting that first execution past a hardened, patched, EDR-monitored endpoint — and it is a moving target, because every technique that works at scale gets a control built against it. This page traces the evolution conceptually: what each delivery format is, why it worked, and what killed it. The point is to understand which control you are testing, not to ship a payload.

The arms race in one table

EraVectorWhat ended it
ClassicVBA macros in .doc/.xls from emailMark-of-the-Web + macros-from-internet blocked by default (2022)

Mark-of-the-Web: the hinge

Almost every defensive advance here rests on one mechanism. When a file is downloaded from the internet, Windows tags it with a Mark-of-the-Web (a zone identifier in an alternate data stream). Office opens MotW-tagged documents in Protected View and refuses to run their macros; SmartScreen checks MotW binaries against reputation. The entire container-file wave existed to break MotW propagation — historically, files extracted from an ISO or a 7-Zip archive did not inherit the mark, so the payload inside ran without the restrictions. Each time a format stopped propagating MotW, that format died as a vector. Understanding this one flag explains the whole timeline.

The format families

  • Office macros (VBA): once the dominant vector; now blocked by default for internet-sourced files. Still relevant internally or where policy has been loosened.
  • Container files (ISO/IMG/VHD/ZIP): used to smuggle a payload past the mark and past some gateways; mostly closed by MotW propagation fixes and ASR.
  • Shortcuts and embedded objects (LNK, OneNote): a shortcut or an embedded file that launches a script host; heavily signatured now.
  • HTML smuggling: the payload is assembled in the browser from JavaScript (a Blob), so nothing malicious crosses the network as a file — it is built client-side. Countered by download inspection and MotW on the reconstructed file.
  • Installers and signed binaries: MSI/MSIX packages and legitimately signed executables that sideload a malicious DLL — trading on trust and reputation rather than hiding.

What the first stage actually does

The document is only the delivery wrapper. What it launches is a loader whose job is to get a C2 agent running in memory while evading the endpoint stack — the subject of Process Injection & Loaders and In-Memory Post-Exploitation Tradecraft. The loader must also get past script and memory scanning — see Modern AMSI & ETW Bypasses — and, on locked-down hosts, past application control (AppLocker & WDAC Bypass).

Detections and controls

  • Attack Surface Reduction (ASR) rules: block Office apps from creating child processes, block executable content from email and script hosts, block Win32 API calls from macros.
  • Keep MotW working: ensure archive tools and mounted images propagate the mark; this is the backbone control.
  • Application control (WDAC/AppLocker): allow-list what may execute, so an unknown loader never starts regardless of how it arrived.
  • Process-lineage telemetry: winword.exe → wscript.exe → rundll32.exe is a textbook maldoc chain; Sysmon/EDR process trees catch it. See Logging & Telemetry.
  • Disable what you do not use: VBA, HTA, and the Windows Script Host are legacy execution surfaces that most environments can turn off entirely.
