Cloud

GCP Attack Paths

2026-10-15 · 10 min read

Google Cloud rounds out the cloud trio alongside AWS and Entra/Azure. GCP's model is distinctive: identity is organised around service accounts, and the key escalation primitives come from the ways one identity is allowed to act as or mint tokens for another. As with the others, cloud attacks here are IAM attacks — hosts are almost incidental.

The GCP identity model

Resources live in a hierarchy: organisation → folders → projects → resources, with IAM policy inherited down the tree. Human users and service accounts (SAs) are granted roles at some level of that hierarchy. SAs are the interesting identities: workloads run as them, and their permissions are frequently broader than they need. The metadata server on a Compute Engine VM hands out the attached SA's access token — the GCP analogue of AWS IMDS.

Getting a foothold identity

EntryMechanism
Leaked SA keyA JSON key file in a repo, image, or bucket authenticates directly and does not expire
SSRF → metadataReach metadata.google.internal to read the VM's SA token (see SSRF)
Public storageOpen Cloud Storage buckets leaking code/keys/data
OAuth consentOver-scoped Workspace app grants

The signature escalation primitives

GCP privilege escalation is largely about impersonation and token minting — a small set of IAM permissions that let one identity become another:

  • Service Account Token Creator (iam.serviceAccounts.getAccessToken): mint access tokens for a more-privileged SA and act as it.
  • actAs / deploy-as: permission to deploy a workload (a function, a VM, Cloud Run) as a privileged SA runs your code with that SA's rights — the GCP cousin of AWS iam:PassRole.
  • Set IAM policy (setIamPolicy) on a project or SA: grant yourself more, directly.
  • SA key creation: create a new key for a privileged SA and authenticate as it.

Each is a one-hop "become a bigger identity" edge; chained across the hierarchy they reach project or organisation ownership. Tools like the GCP IAM privilege-escalation research sets and enumeration via gcloud map these edges.

Lateral movement, data, and persistence

  • Lateral: impersonation chains across SAs and projects; the org hierarchy means a high-level grant reaches many projects at once.
  • Data: Cloud Storage buckets, BigQuery datasets, and Secret Manager are the targets once you hold a capable identity.
  • Persistence: a fresh SA key (long-lived), an added IAM binding, or a scheduled job keep access even after the entry is closed.

Detection & hardening

  • Kill long-lived SA keys; prefer workload identity and short-lived tokens; alert on SA key creation.
  • Constrain impersonation and actAs; treat Token Creator and setIamPolicy as highly privileged and grant them narrowly.
  • Enforce the metadata token endpoint protections and segment workloads so SSRF cannot reach a powerful SA.
  • Mine Cloud Audit Logs for generateAccessToken, setIamPolicy, and key-creation events — the escalation edges above all appear there.
