Cloud

GCP Attack Paths

2026-10-15 · 10 min read

Google Cloud rounds out the cloud trio alongside AWS and Entra/Azure. GCP's model is distinctive: identity centres on service accounts, and the escalation primitives come from the ways one identity is allowed to act as or mint tokens for another. As with the others, cloud attacks here are IAM attacks — hosts are almost incidental.

The identity model

Resources sit in a hierarchy — organisation → folders → projects → resources — with IAM policy inherited down the tree. Human users and service accounts (SAs) hold roles at some level of it. SAs are the interesting identities: workloads run as them and their permissions are often broader than they need. A Compute Engine VM's metadata server hands out the attached SA's token, the GCP analogue of AWS IMDS.

Orient once you have any identity

gcloud auth list ; gcloud config list        # who am I, which project
gcloud projects list
gcloud iam service-accounts list
# what can this identity do? test it against a resource:
gcloud projects get-iam-policy <project> --format=json
# from a VM / via SSRF — read the attached SA token
curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"

The signature escalation primitives

GCP privilege escalation is largely impersonation and token minting — a small set of IAM permissions that let one identity become another. Chained across the hierarchy they reach project or org ownership:

# Service Account Token Creator: mint a token for a MORE privileged SA, act as it
gcloud iam service-accounts get-access-token <priv-sa>@<proj>.iam.gserviceaccount.com \
  --impersonate-service-account=...
# actAs / deploy-as: run your code AS a privileged SA (GCP cousin of iam:PassRole)
gcloud functions deploy x --run-service-account <priv-sa> --trigger-http ...
# setIamPolicy on a project/SA: grant yourself more, directly
# create a new key for a privileged SA and authenticate as it
gcloud iam service-accounts keys create k.json --iam-account <priv-sa>

These map to the well-known GCP privesc research; enumerate which ones you hold and walk the chain. iam.serviceAccounts.signBlob / signJwt are a quieter variant — forge a token for an SA without ever creating a key.

Check the default service account before assuming Editor. The default Compute/App Engine SAs were historically granted project Editor, so a metadata-token read was usually a strong identity. Organisations created since ~mid-2024 may switch that off with the iam.automaticIamGrantsForDefaultServiceAccounts org policy, so read the token’s real roles rather than assuming it is Editor.

Lateral movement, data and persistence

  • Lateral: impersonation chains across SAs and projects; a high-level grant reaches many projects at once.
  • Data: Cloud Storage, BigQuery and Secret Manager once you hold a capable identity (gcloud secrets versions access).
  • Persistence: a fresh SA key (long-lived), an added IAM binding, or a scheduled job keep access after the entry closes.

Detection & hardening

  • Kill long-lived SA keys; prefer workload identity and short-lived tokens; alert on key creation.
  • Constrain impersonation and actAs; treat Token Creator and setIamPolicy as highly privileged.
  • Protect the metadata endpoint and segment workloads so SSRF cannot reach a powerful SA.
  • Mine Cloud Audit Logs for GenerateAccessToken, SetIamPolicy and key-creation events — the escalation edges all appear there.
