Browser Credential & Token Theft

2026-10-15 · 9 min read

The browser holds the keys to everything: saved passwords, autofill, and — most valuable — the session cookies that represent already-authenticated, MFA-satisfied logins. With code execution on an endpoint, an attacker who reads the browser's stores inherits the victim's logged-in sessions without touching a password or a second factor. This is the local counterpart to the proxy-based theft in AiTM, Token & Session Theft.

What the browser stores, and where

Chromium-based browsers keep this in per-profile SQLite databases, with the sensitive values encrypted under a key bound to the OS user (DPAPI on Windows — see DPAPI Abuse):

# Windows (Chrome)
%LOCALAPPDATA%\Google\Chrome\User Data\Default\Network\Cookies
%LOCALAPPDATA%\Google\Chrome\User Data\Default\Login Data   # saved passwords
%LOCALAPPDATA%\Google\Chrome\User Data\Local State          # wraps the AES key (DPAPI)
# Linux
~/.config/google-chrome/Default/Cookies
# the cookie/login DBs are just SQLite:
sqlite3 Cookies "SELECT host_key,name,encrypted_value FROM cookies;"

The crucial point: the protection is bound to the user, so code running as that user can ask the OS to decrypt the data legitimately — no cracking required.

App-Bound Encryption, and why cookie theft got harder

Because cookie theft became rampant, Chrome added App-Bound Encryption (ABE): the cookie key is additionally wrapped so that, in principle, only the browser itself (validated through a privileged service) can unwrap it, not any process running as the user. This broke the simple "copy the DB, decrypt with DPAPI" tooling and triggered a fresh round of bypass research. The known bypasses run code from inside Chrome’s own install directory, inject a trusted Chrome process, or abuse the elevation service over COM (the no-admin COM-hijack in CyberArk’s “C4 Bomb”). The lesson for a defender: cookie protection is now a moving target and is not sufficient on its own.

Session cookies are the prize

A stolen session cookie is bearer material: imported into the attacker's browser, it resumes the victim's authenticated session until it expires or is revoked. Because the original login already satisfied MFA, replaying the cookie does not prompt for it again. This is why "we have MFA" is not a complete answer to credential phishing — the session, not the password, is the asset.

Beyond cookies

  • Cloud CLI caches — ~/.aws/credentials, ~/.azure, ~/.config/gcloud hold long-lived keys and refresh tokens, often unencrypted.
  • Password managers — an unlocked vault, or its browser extension's session, is a single point of total compromise.
  • SSO helper tokens and primary refresh tokens on managed Windows (see the token-theft page).

Detection & mitigation

  • Watch access to browser stores — a non-browser process reading another browser's Cookies/Login Data file is a strong signal (EDR, Sysmon file-access and ProcessAccess events).
  • Bind sessions to device/network via conditional access and enable continuous access evaluation, so a stolen cookie replayed elsewhere fails.
  • Phishing-resistant MFA and short session lifetimes reduce the window and value of a stolen session.
  • Keep ABE and the browser current; manage browsers so saved-password and sync policy is controlled.
  • EDR on the endpoint — local token theft presupposes code execution; the earlier you catch that, the less the browser matters.
