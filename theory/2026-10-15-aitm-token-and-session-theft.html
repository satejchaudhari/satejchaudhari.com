AiTM, Token & Session Theft

2026-10-15 · 10 min read

Multi-factor authentication stopped password phishing from working on its own, so attackers stopped targeting the password and started targeting the session. Once a user has authenticated and cleared MFA, the service issues a token — a cookie, an OAuth refresh token, an Entra primary refresh token. Steal or relay that token and you are the user without the password and without the second factor. This is the defining initial-access and credential-access technique of the current era.

Why MFA is not the finish line

MFA authenticates the login event. The artefact it produces — the session token — is bearer material: whoever holds it is treated as the user until it expires or is revoked. Conditional access can bind a session to a device or network, but where it does not, the token is portable. Every attack below is about getting that token.

Adversary-in-the-Middle (AiTM) phishing

A reverse-proxy phishing kit (the archetype is Evilginx) sits between the victim and the real login page. The victim sees the genuine site — because they are talking to it, through the proxy — enters their password, and completes MFA against the real service. The proxy relays every request and, on success, captures the session cookie. The operator imports that cookie and is inside the account. Because the victim authenticated to the real origin, this defeats push/OTP/SMS MFA entirely.

# the stolen artefact is the authenticated session cookie, e.g. Entra's ESTSAUTH.
# it is replayed by adding it to a browser session — no re-auth, no MFA prompt:
document.cookie = "ESTSAUTHPERSISTENT=<stolen-value>; domain=.login.microsoftonline.com"

Device-code phishing

The OAuth device-code flow is meant for input-constrained devices (a TV). The attacker starts the flow, gets a user code, and phishes the victim to enter that code at the genuine microsoft.com/devicelogin page. The victim authenticates and consents on the real site; the attacker's device receives the tokens:

# 1. attacker requests a device code for a first-party client id
POST https://login.microsoftonline.com/common/oauth2/v2.0/devicecode
     client_id=<first-party-app>&scope=https://graph.microsoft.com/.default offline_access
# 2. victim is lured to enter the returned user_code at the real devicelogin page
# 3. attacker polls the token endpoint and receives access + refresh tokens
#    (TokenTactics / roadtx automate the poll-and-collect)

The Entra primary refresh token (PRT)

On Entra-joined Windows the PRT is a long-lived token that silently signs the user in to cloud apps. It is TPM-protected, but malware running as the user can request PRT-derived cookies through the normal broker interfaces. Lower-hanging fruit sits in CLI caches:

az account get-access-token --resource https://graph.microsoft.com   # cached token
ls ~/.azure/  ;  type %USERPROFILE%\.azure\msal_token_cache.json      # token caches

OAuth consent & browser token theft

An illicit consent grant asks the user to approve a rogue app with broad delegated scopes (mail, files); once approved, the app holds a refresh token that survives password resets and most MFA, because no further interactive login is needed. With code execution on an endpoint you skip the proxy entirely and read cookies from the browser profile — see Browser Credential & Token Theft.

What actually stops it

  • Phishing-resistant MFA (FIDO2 / WebAuthn / passkeys) — the authenticator is bound to the real origin, so an AiTM proxy on another domain cannot complete the ceremony. The one control that breaks the class.
  • Token binding & conditional access — bind sessions to a compliant/managed device and known network so a stolen cookie replayed from attacker infrastructure fails; shorten lifetimes.
  • Continuous access evaluation — revoke sessions in near-real time on risk signals rather than waiting for expiry.
  • App-consent governance — block user consent to unverified apps; review risky grants; disable device-code flow where unused.
  • Detect impossible-travel/new-ASN sign-ins on an existing session, token use from an unexpected device, and sudden app consents.
