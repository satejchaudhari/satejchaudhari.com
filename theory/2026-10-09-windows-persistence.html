Windows Persistence

2026-10-09 · 10 min read

Persistence is how access survives a reboot, a logout, or a killed beacon. On Windows the menu is large because many legitimate mechanisms run code automatically; the operator picks one that is reliable, matches the privilege held, and is quiet enough not to light up the EDR. Defenders read the same list in reverse — these are the autoruns to baseline and watch. This page catalogues the techniques by trigger.

Scheduled tasks & services

The two most reliable high-privilege mechanisms. A scheduled task can fire on logon, at boot, on a timer or on an event; a service starts at boot and typically runs as SYSTEM. Both are first-class, documented admin features, which is exactly why they are abused and why new ones should be alerted on.

WMI event subscriptions

A fileless, SYSTEM-level trigger: a permanent WMI subscription pairs an event filter (a condition such as a given uptime or a process starting) with a consumer that runs a command. It survives reboots and lives in the WMI repository rather than on disk, which is why it is a red-team favourite — and why Sysmon events 19–21 exist to catch it.

Hijacks that ride trusted code

  • DLL search-order / sideloading — a malicious DLL placed where a trusted application loads it; the app runs the code whenever it starts.
  • COM hijacking — pointing a frequently-instantiated CLSID under the per-user class store at an attacker DLL (no admin needed).
  • Service / task binary replacement — overwriting a binary a privileged task already runs (overlaps with weak-permission privesc).
  • Phantom DLLs — supplying a DLL a service looks for but does not ship.

Accessibility & account backdoors

  • Accessibility binaries — tampering with or Image-File-Execution-Options-hijacking the ease-of-access binaries gives a SYSTEM shell from the logon screen (effective but loud and well-signatured).
  • Rogue local admin / RID hijack — adding an account, or aliasing one to the built-in administrator RID.
  • Remote-access tweaks — enabling RDP and sticky-key style re-entry.
Reliability versus noise is the whole decision. Run keys and scheduled tasks are reliable but heavily monitored; WMI subscriptions and COM hijacks are quieter but fiddlier. In an AD environment, domain-level persistence (next page) usually beats host-level because it survives reimaging the endpoint.

Detection & hardening

  • Baseline autoruns (Sysinternals Autoruns) and alert on new Run keys, services, scheduled tasks and WMI subscriptions (Sysmon 12–13, 19–21 — see Logging).
  • Watch for DLLs loading from user-writable paths and unusual per-user CLSID writes.
  • Application allow-listing (AppLocker/WDAC) limits what a persisted payload can run.
  • Alert on accessibility-binary tampering and IFEO debugger values.
