Logging & Telemetry — From Event to SIEM

2026-10-09 · 18 min read

Every detection, every investigation, and every bit of forensic timeline work ultimately rests on logs. If an action was not recorded somewhere, in a form that reached a place you can query, it effectively did not happen as far as the SOC is concerned. This page is a ground-up reference on logging for defenders: what a log is, where logs come from, the formats and schemas they travel in (syslog, CEF, LEEF, JSON, EVTX and the normalisation standards), Windows Event Log and the security Event IDs that matter, Sysmon in depth with its full event catalogue, Linux auditing, the pipeline that carries all of it into a SIEM, and how log integrity is kept and attacked. It pairs with the SOC and Detection Engineering pages, which cover what you do with the logs once they land.

What a log actually is

A log is a timestamped record of a discrete event — "this happened, here, then." Strip away the format and almost every log entry carries the same handful of fields:

  • Timestamp — when the event occurred (and ideally when it was recorded and received — the three can differ).
  • Source — the host, device, application or sensor that produced it.
  • Severity / priority — how important the producer thinks it is.
  • Event identity — a category, signature, or Event ID that says what kind of thing happened.
  • Body / fields — the specifics: who, what, which object, source and destination, outcome.

The single most important distinction is structured vs unstructured. An unstructured log is a line of free text (Failed password for root from 10.0.0.5) that a parser must pull fields out of with regex. A structured log carries named fields already ({"event":"ssh_login","result":"fail","user":"root","src":"10.0.0.5"}), so it is machine-readable without guessing. Modern logging pushes everything toward structure, because unparsed text does not scale to billions of events a day and breaks silently when a message format changes.

Log formats and schemas

A log's format is how its fields are encoded on the wire or on disk; a schema is the agreed set of field names everything is normalised into after collection. Both matter: formats decide how hard parsing is, schemas decide whether a query written once works across every source.

Syslog — the common carrier

Syslog is both a message format and a transport, and it underpins most of the others. Each message carries a PRI value computed as facility × 8 + severity, so one integer encodes both what subsystem produced the event and how urgent it is. The severities run 0–7:

CodeSeverityCodeSeverity
0Emergency4Warning
1Alert5Notice
2Critical6Informational
3Error7Debug

The older RFC 3164 ("BSD syslog") is loose and has a low-resolution timestamp with no year or timezone; the newer RFC 5424 fixes this with ISO-8601 timestamps, explicit hostnames and app names, and a structured-data section. Syslog travels over UDP/514 (fire-and-forget, lossy), TCP/514 (reliable), or TLS/6514 (encrypted). A typical RFC 5424 line: 

<34>1 2026-10-09T22:14:15.003Z web01 sshd 1234 ID47 - Failed password for root from 10.0.0.5 port 4242
# <34> = PRI: facility 4 (auth) * 8 + severity 2 (critical)
# then: version, timestamp, host, app, PID, msg-id, structured-data (-), message

CEF — the SIEM workhorse

The Common Event Format is what a huge number of security products speak into a SIEM. It is a fixed pipe-delimited header followed by a free-form set of key=value pairs using standardised dictionary keys (src, dst, spt, dpt, suser, act, and so on): 

CEF:0|Security|Threatmanager|1.0|100|worm successfully stopped|10|src=10.0.0.1 dst=2.1.2.2 spt=1232 suser=jsmith act=blocked

# header fields, in order:
# CEF:Version | Device Vendor | Device Product | Device Version
#   | Signature ID | Name | Severity | Extension (key=value ...)

The seven header fields are mandatory and positional; everything after the final pipe is the extension dictionary. LEEF (QRadar's format) is the same idea with a slightly different header (LEEF:2.0|Vendor|Product|Version|EventID|) and a declarable delimiter for its key/value body.

Normalisation schemas

Formats get a log in; a schema makes logs from different sources comparable. Rather than write one detection for a Cisco firewall and another for a Palo Alto, you map both into a common field model and write the rule once. The ones worth knowing:

  • ECS (Elastic Common Schema) — the field model behind the Elastic Stack (e.g. source.ip, event.action, user.name).
  • OCSF (Open Cybersecurity Schema Framework) — a vendor-neutral schema backed by AWS, Splunk and others, increasingly the lingua franca for security data lakes.
  • CIM (Splunk Common Information Model) — Splunk's normalisation model that its detections and dashboards key on.
  • OpenTelemetry — the observability standard unifying logs, metrics and traces, now with a logging data model.
Rule of thumb: formats are a parsing problem, schemas are a coverage problem. A new format just needs a parser; a new schema decision affects every detection you have ever written. Pick a schema early and map everything to it.

Windows Event Log

Windows is the richest logging environment most defenders deal with. Events are written by providers into channels, stored as binary .evtx, and rendered as XML. The classic channels are Security, System, Application and Setup, alongside hundreds of per-component Operational logs (PowerShell, Sysmon, Windows Defender, Task Scheduler, and so on). Each event has a numeric Event ID that identifies what happened, scoped to its provider.

Many high-value events are off by default and must be turned on through Advanced Audit Policy — process-creation auditing (4688, ideally with command-line capture) and object-access auditing are the usual first wins. The security Event IDs that recur in investigations:

At scale these are shipped off the host with Windows Event Forwarding (WEF) to a Windows Event Collector, or by an agent (Winlogbeat, the Elastic/Splunk agents, NXLog), so that clearing a local log no longer destroys the evidence.

Sysmon — endpoint visibility done right

The default Windows logs leave large gaps: no network-connection record per process, no image-load detail, thin registry coverage. Sysmon (System Monitor, from Sysinternals) fills them. It installs a driver and a service that watch the system and write richly-detailed events to the Microsoft-Windows-Sysmon/Operational channel — crucially, including the SHA/MD5/IMPHASH hashes of images, the parent process lineage, and a stable ProcessGUID that lets you stitch activity together across events. It is the single highest-value free source of endpoint telemetry, and most detection content assumes it is present.

Sysmon is driven entirely by its configuration file: an XML policy of include/exclude filters that decides what is logged, because logging everything would bury the signal. The widely-used community baselines (SwiftOnSecurity's config, and Olaf Hartong's modular sysmon-modular, which is mapped to MITRE ATT&CK) are the normal starting point. Its event catalogue:

Sysmon Event 1 (process creation with command line, hashes and parent) plus Event 3 (network) and Event 10 (process access, for LSASS) cover an enormous share of real-world attacker behaviour. If you do nothing else on an endpoint, get those three flowing into the SIEM.

Linux and Unix logging

The Unix world splits into the traditional text pipeline and the Linux audit subsystem:

  • syslog daemons — rsyslog and syslog-ng receive, filter and forward syslog, writing to /var/log/ (auth.log or secure for authentication, messages/syslog for general events).
  • journald — systemd's binary, indexed journal, read with journalctl; it can forward to a syslog daemon for shipping.
  • auditd — the Linux Audit framework, the closest analogue to Windows security auditing. Kernel-level rules (watch a file, watch a syscall) produce detailed records read with ausearch/aureport. It is the source for execution, file-access and privilege-change visibility on Linux, and the basis of many container/host EDR sensors. 
# auditd rule: record every execve (process execution) with a searchable key
-a always,exit -F arch=b64 -S execve -k proc_exec
# then review:
ausearch -k proc_exec --start today | aureport -x --summary

The pipeline: from event to SIEM

A log is only useful once it reaches somewhere you can search it. Every mature logging setup is a pipeline with the same stages, and problems at any stage silently cost you visibility:

  1. Generate — the source emits the event (and you must have enabled the right auditing for it to exist at all).
  2. Collect — an agent or receiver gathers it: Winlogbeat / Elastic Agent, Splunk Universal Forwarder, Fluent Bit / Fluentd, NXLog, or a syslog daemon.
  3. Transport — ship it off-host, ideally encrypted and buffered (TLS syslog, a message queue like Kafka) so a burst or an outage does not drop events.
  4. Parse & normalise — extract fields and map them into your schema (ECS/OCSF/CIM) so detections are source-agnostic.
  5. Enrich — add context the raw event lacks: GeoIP, asset owner and criticality, threat-intel matches, user identity.
  6. Store & index — land it in the SIEM/data lake with hot/warm/cold tiers to balance query speed against retention cost.
  7. Analyse — detections, dashboards, hunting and investigation run on top (see the Detection Engineering page).

The economics matter as much as the plumbing. SIEM licensing and storage are usually priced on volume, so teams filter at the edge (drop known-noise events), sample high-volume low-value sources, and route full-fidelity copies to cheaper storage. Over-collecting a noisy source while missing a quiet, high-value one is the most common and most expensive logging mistake.

Log integrity, retention and time

Logs are evidence, and evidence has requirements beyond "it exists somewhere":

  • Time synchronisation. Correlating across hosts is impossible if clocks drift, so every source runs NTP and logs should be normalised to UTC on ingest. Keep the three timestamps — event time, collection time, ingest time — distinct.
  • Tamper-resistance. The first thing an intruder does is try to cover tracks: clearing the Windows Security log (Event 1102), stopping the Sysmon or EDR service, deleting /var/log files, or disabling auditing (ATT&CK T1562 Impair Defenses / T1070 Indicator Removal). The defence is to get logs off the host immediately — WEF, agent forwarding, remote syslog — so the authoritative copy is somewhere the attacker on the endpoint cannot reach, and to alert on the tamper events themselves (1102, Sysmon service-state change, audit-policy changes).
  • Retention. Driven by both investigation needs (dwell time can be months, so short retention blinds you to the start of an intrusion) and compliance (e.g. PCI-DSS wants a year, with ninety days immediately available).
  • Coverage, not volume. The goal is the events that answer attacker techniques, not the most gigabytes — map your logging to ATT&CK and verify the detections you care about actually have the data they need.

The takeaway

Logging is the substrate everything defensive stands on: you cannot detect, investigate or prove what you never recorded. The craft is in choosing the right sources (OS, endpoint, identity, network, cloud), getting them into clean formats and a single schema, enabling the auditing that makes the valuable events exist at all (Advanced Audit Policy, Sysmon with a good config), and running a pipeline that ships everything off-host into a SIEM where it is durable, time-correct and searchable. Do that well and the detection and response work the rest of the Blue Team pages describe has something solid to stand on; skimp on it and every layer above inherits the blind spots.
