Insecure Deserialization

2026-10-15 · 9 min read

Insecure deserialization is one of the highest-impact web bugs because it so often lands as remote code execution. Applications serialise objects to store or transmit them; if they later turn attacker-controlled bytes back into live objects without validation, the attacker influences what gets built — and in many languages, what runs during the rebuild.

Spot the format

Serialized blobs have recognisable shapes. Any of these arriving from a client (in a cookie, hidden field, header, or API body) is a red flag:

Java          AC ED 00 05 …      base64 starts  rO0AB…
.NET          AAEAAAD/////…      or a __VIEWSTATE field
PHP           O:4:"User":2:{…}   (serialize() output)
Python pickle \x80\x04… (opcodes)  often base64 in a cookie
Ruby          \x04\b…  (Marshal)

Why it becomes RCE: gadget chains

The attacker rarely needs the app's own classes to be malicious. They assemble a gadget chain — methods already present in the app's libraries that, triggered during deserialisation (constructors, readObject, PHP __wakeup/__destruct), chain into a dangerous operation. You do not hand-build these; generators ship ready chains:

# Java — generate a payload for a known library gadget, then send it where the
# app deserializes (cookie, parameter, RMI/JMX, etc.)
java -jar ysoserial.jar CommonsCollections6 'id' | base64 -w0

# .NET equivalent
ysoserial.exe -g TypeConfuseDelegate -f BinaryFormatter -c "calc.exe"

# PHP — phpggc catalogues framework gadget chains
phpggc Laravel/RCE1 system id

The key point: the vulnerability is deserialising untrusted data at all. The gadgets are just the libraries you already ship.

Confirming it blind

Often nothing comes back, so confirm the sink is live before chasing RCE: send a gadget whose only effect is an outbound callback. Java’s URLDNS chain triggers a DNS lookup when the bytes are deserialised, so a hit on your listener proves the sink fired even with no code execution — the deserialisation analogue of confirming blind SSRF. A sleep/timing gadget serves the same confirm-first purpose where even DNS is blocked.

Where serialized data shows up

LocationExample
Cookies / session tokensBase64 Java/PHP object in a cookie
Hidden fields / ViewState.NET __VIEWSTATE (no/weak MAC)
APIs with typed formatsYAML/XML with type tags, pickle endpoints
Caches & queuesSerialized objects passed between services

Prevention

  • Do not deserialise untrusted input into live objects. Prefer plain data formats (JSON without type resolution) and map fields explicitly.
  • If unavoidable, enforce a strict type allow-list (look-ahead / resolve-class filtering) and sign-then-encrypt any state the client round-trips so it cannot be tampered with.
  • Retire dangerous APIs — .NET BinaryFormatter, Python pickle on untrusted data, unsafe YAML loaders.
  • Detect serialized magic bytes from clients, deserialisation exceptions, and unexpected child processes from app servers.
