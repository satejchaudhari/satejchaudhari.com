Insecure Deserialization

2026-10-15 · 9 min read

Insecure deserialization is one of the most impactful web bugs because it so often leads directly to remote code execution. Applications serialise objects to store or transmit them; if they later deserialise attacker-controlled data back into live objects without validation, the attacker can influence what gets instantiated and what runs during that reconstruction.

Serialisation in one minute

Serialisation turns an in-memory object into a byte stream (Java serialized objects, .NET BinaryFormatter/ViewState, Python pickle, PHP serialize(), Ruby Marshal, or structured formats like YAML/JSON with type hints). Deserialisation reverses it. The danger is that in many languages this process can execute code — constructors, magic methods, or type handlers run as the object is rebuilt.

Why it becomes RCE: gadget chains

The attacker rarely needs the app's own classes to be malicious. Instead they assemble a gadget chain: a sequence of methods already present in the application's libraries that, when triggered during deserialisation, chain together into a dangerous operation such as command execution. Tools like ysoserial (Java) and ysoserial.net catalogue these chains for common libraries. The key insight is that the vulnerability lives in deserialising untrusted data at all — the gadgets are just the libraries you already ship.

Spotting it

Recognisable magic bytes give it away: Java streams begin ac ed 00 05 (Base64 rO0), .NET and PHP have characteristic shapes, Python pickle its opcodes. Any such blob coming from the client is a red flag.

Detection & prevention

  • Do not deserialise untrusted input into live objects. Prefer simple data formats (plain JSON without type resolution) and map fields explicitly.
  • If you must, sign/encrypt serialized state so the client cannot tamper with it, and enforce strict type allow-lists (look-ahead deserialisation, resolve-class filters).
  • Retire dangerous APIs (BinaryFormatter, unsafe YAML loaders, pickle on untrusted data).
  • Detection: serialized magic bytes from clients, deserialisation exceptions, and unexpected child processes from app servers (an RCE gadget firing).
