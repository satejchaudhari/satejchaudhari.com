Server-Side Request Forgery (SSRF)

2026-10-15 · 9 min read

Server-Side Request Forgery (SSRF) is the bug that turns a web application into a proxy for the attacker. You make the server issue a request of your choosing, and because that request originates from inside the network, it reaches places you never could from outside: cloud metadata endpoints, internal admin panels, databases, and other services that trust "internal" traffic. In cloud environments SSRF is frequently the single step between a web bug and full account compromise.

Why it exists

Any feature that fetches a URL on the user's behalf is a candidate: webhooks, link previews, PDF/image generators, document importers, "import from URL", SSO/OpenID discovery, and server-side HTTP clients. If the destination is taken from user input and the server does not restrict where it may connect, the user controls the server's outbound request.

What makes it dangerous: implicit trust

Internal services routinely skip authentication because they assume only trusted internal callers can reach them. SSRF breaks that assumption. The highest-impact target is the cloud instance metadata service (the link-local 169.254.169.254 address), which hands out the instance's IAM role credentials — see the Cloud Attack Path Explorer and AWS Attack Paths. From there SSRF becomes privilege escalation into the cloud account.

SSRF targetPayoff
Cloud metadata (169.254.169.254)IAM role credentials → cloud account access
Internal admin panels / dashboardsUnauthenticated management access
Internal APIs & databasesData access, further pivot
localhost servicesDebug endpoints, actuators, unauth daemons

Blind vs non-blind

If the response comes back to you, SSRF is non-blind and you can read internal content directly. If it does not, it is blind — you confirm it out-of-band (the server connects to a collaborator host you control) and exploit it through side effects and timing. Blind SSRF is still dangerous: it is enough to hit the metadata endpoint or trigger internal state-changing requests.

Why filters fail

Naive defences block localhost or 169.254.169.254 by string match. These are routinely bypassed with alternative encodings, alternate IP representations, DNS names that resolve to internal addresses, and redirect chains where an allowed host 302s to an internal one. The lesson is that deny-lists do not work for SSRF; the destination must be validated positively.

Detection & prevention

  • Allow-list destinations: validate the resolved IP against an explicit allow-list after DNS resolution, and re-validate on redirects.
  • Block link-local and internal ranges at the egress layer; put fetchers in a segmented network with no route to metadata or admin.
  • Enforce IMDSv2 (session-token metadata) so a simple SSRF cannot read instance credentials.
  • Disable unused URL schemes (file://, gopher://, dict://) and cap response size/redirects.
  • Detection: outbound requests from app servers to link-local/internal addresses, and fetches to unexpected hosts.
