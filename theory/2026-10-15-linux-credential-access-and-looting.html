Linux Credential Access & Looting

2026-10-15 · 9 min read

On Linux, credential access is mostly a looting exercise: secrets are rarely in a single protected store the way Windows keeps them, they are scattered across the filesystem, process memory, and the home directories of every user and service. Once you have a shell — even an unprivileged one — the job is to harvest what reuses elsewhere and what escalates. This pairs with Linux Privilege Escalation (which turns found secrets into root) and Data Collection & Exfiltration.

Where Linux secrets live

LocationWhat you find
Home dotfiles.bash_history, .ssh/ keys, .aws/.config/gcloud, .netrc, .git-credentials
App & web configsDB connection strings, API keys, wp-config.php, .env, settings files
Service configsCredentials for databases, backups, mail, monitoring under /etc and /opt
Process memory & argsPasswords passed on command lines (visible in /proc/*/cmdline), env vars
/etc/shadowPassword hashes — only readable as root; a crackable prize
Logs & backupsSecrets leaked into logs, tarballs, and old copies

The hashes: /etc/passwd and /etc/shadow

User accounts are in world-readable /etc/passwd; the password hashes are in root-readable /etc/shadow. If you can read shadow (as root, or via a misconfiguration), the hashes crack offline — see Password Cracking. A writable /etc/passwd is an instant escalation: historically you could add a user with a known password hash.

SSH keys are the Linux crown jewels

Private keys in ~/.ssh/ are reusable credentials that frequently move you laterally to other hosts with no password at all. known_hosts and authorized_keys map the network for you — which hosts this identity can reach and which identities can reach this host. Harvesting keys and mapping those relationships is a core lateral-movement enabler (see Linux Lateral Movement & SSH).

Process and memory sources

Credentials passed as command-line arguments are visible to any user via /proc/<pid>/cmdline; environment variables of your own processes (and sometimes others) hold tokens. Long-running services sometimes hold secrets in memory that root can read. Automated looters (LinPEAS, linux-smart-enumeration) sweep all of the above.

Detection & hardening

  • Least privilege on secret files: strict permissions on keys, configs, and backups; never world-readable credentials.
  • Don't pass secrets on command lines; use files or secret managers so they do not appear in /proc or shell history.
  • Protect and monitor /etc/shadow and key directories; alert on reads by unexpected users.
  • auditd rules on sensitive files and on execution of known looters; ship to a SIEM — see Logging & Telemetry.
