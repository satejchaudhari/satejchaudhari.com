AWS Attack Paths

2026-10-09 · 11 min read

AWS attacks are IAM attacks. The hosts matter less than the identities and the permissions between them — who can assume which role, read which secret, or run code as what. A single leaked key or an over-broad policy is usually enough to start a chain that ends in account takeover. This page maps the recurring AWS paths.

Getting credentials

  • Leaked access keys — long-lived AKIA... keys in repos, laptops, CI logs and config.
  • SSRF → instance metadata — a server-side request to the metadata service (IMDS) returns the EC2 role's temporary credentials (see the workflow).
  • Over-permissioned CI/CD & Lambda — build and function roles whose rights far exceed their task.
  • Exposed services — public S3 buckets, open databases and management interfaces holding secrets.

Orient first

aws sts get-caller-identity          # who am I
aws iam get-account-authorization-details   # the whole IAM picture (if allowed)
# enumerate what THIS identity can do, then look for a privesc edge
# tools: enumerate-iam, ScoutSuite / Prowler (posture), pacu (exploitation framework)

IAM privilege escalation

AWS has a well-catalogued set of IAM-permission combinations that let a low-privileged identity become administrator. The theme: a permission that lets you grant yourself more, directly or by running code as a more privileged role.

Permission patternEscalation
iam:CreatePolicyVersion / AttachUserPolicyAttach an admin policy to yourself.
iam:PassRole + a compute service (ec2:RunInstances, lambda:*, Glue, CloudFormation...)Pass a more-privileged role to something you launch, then act as that role.
iam:CreateAccessKey on another userMint keys for a more-privileged user.
sts:AssumeRole with a permissive trust policyAssume a role you were not meant to.
The mental model is a graph of who can assume / pass / modify whom — the AWS analogue of a BloodHound path. Tools map these privesc edges automatically; the win is almost always an iam:PassRole or a self-policy-attach away.

Lateral movement & data

  • Role assumption chains — hop between roles and, via trust policies, into other accounts in the organisation.
  • SSM / run-command — with the right permissions, run commands on EC2 instances without SSH.
  • Secrets — Secrets Manager, SSM Parameter Store, and env vars hold the next set of credentials.
  • Data — S3, RDS snapshots, and EBS snapshots are the usual objective; snapshot-and-restore sidesteps access controls on the live resource.

Persistence

  • Extra access keys on a user; a new IAM user or role with a permissive trust policy.
  • A Lambda backdoor triggered on a schedule or event; a modified trust policy that lets an external account assume a role.
  • These are the cloud equivalents of host persistence — and just as important to hunt for in IAM/CloudTrail.

Detection & hardening

  • Least privilege & no long-lived keys — prefer roles and short-lived STS tokens; scope PassRole tightly.
  • IMDSv2 (session-based) to blunt SSRF-to-credentials; egress controls around metadata.
  • CloudTrail + GuardDuty — monitor for anomalous API calls, new keys/policies, cross-account assumes and snapshot sharing; ship logs centrally (see Logging).
  • Posture tools (Prowler/ScoutSuite) to find the privesc edges before an attacker does.
