Linux Lateral Movement & SSH

2026-10-15 · 9 min read

Lateral movement on Linux estates runs on trust relationships, and the dominant one is SSH. Where Windows networks move on Kerberos tickets and NTLM hashes, Linux networks move on SSH keys, agent forwarding, and the assumption that "this host can already reach that host". This builds on Linux Credential Access & Looting and the protocol-agnostic Pivoting & Tunnelling.

Key reuse

A private key harvested from one host often unlocks several others, because teams reuse a key across a fleet or a deployment identity is authorised widely. Match keys to hosts and walk the graph:

chmod 600 id_rsa
ssh -i id_rsa user@next-host          # reuse the key directly
# authorized_keys on each host lists who may log in; a matching private key
# elsewhere is a ready-made path.

Agent forwarding and hijacking

SSH agent forwarding (ssh -A) lets a remote host use your local keys for onward hops — convenient, and dangerous. If you land on a host where a higher-privileged user has a forwarded agent, you can use their agent to authenticate onward as them, without ever seeing the key. It is the Linux analogue of token theft:

# find a forwarded agent socket owned by another user (as root)
ls -l /tmp/ssh-*/agent.*
SSH_AUTH_SOCK=/tmp/ssh-XXXX/agent.1234 ssh-add -l   # list that agent's keys
SSH_AUTH_SOCK=/tmp/ssh-XXXX/agent.1234 ssh victim@target   # auth as them

The trust mechanisms, and how they move you

MechanismHow it moves you
Reused private keysOne key authenticates to many hosts
Forwarded SSH agentUse another user's keys via their agent socket
known_hosts / configMaps the network and preferred jump hosts
Host-based auth / NFS trustHosts trust each other by identity, not user
CI/CD & orchestration keysDeployment identities reach the whole fleet

Pivoting through SSH

SSH is also the transport for reaching networks you cannot route to directly:

ssh -L 8080:10.0.0.5:80 user@pivot      # local: reach the target's :80 on your :8080
ssh -R 9001:127.0.0.1:9001 user@you     # remote: expose YOUR service to the target net
ssh -D 1080 user@pivot                  # dynamic SOCKS proxy -> use with proxychains
ssh -J user@pivot user@deep-host        # ProxyJump: chain through a bastion

The non-SSH alternatives (chisel, ligolo-ng, SOCKS over C2) are in Pivoting & Tunnelling; the point here is that a single SSH foothold usually reaches an entire internal segment.

Other Linux lateral vectors

  • Reused service credentials — a DB/API password from one host authenticating to a shared backend.
  • Orchestration planes — Ansible, Salt, Puppet and Kubernetes control planes run commands fleet-wide; own the controller and you reach everything it manages.
  • NFS and shared mounts — writable shared storage used by multiple hosts can carry payloads or leak keys.

Detection & hardening

  • Unique, passphrase-protected keys; inventory and rotate them; prefer short-lived SSH certificates over long-lived keys.
  • Disable agent forwarding to untrusted hosts; prefer ProxyJump over -A.
  • Harden sshd (no host-based auth, no root login) and segment the network.
  • Detect logins from unexpected source hosts, one key used across many hosts quickly, and new SOCKS/forward sessions — ship SSH auth logs to a SIEM.
