Windows Token Abuse & Potato Attacks

2026-10-09 · 11 min read

On Windows, what a process can do is decided by its access token and the privileges that token holds. A handful of those privileges are, in practice, local admin or SYSTEM in disguise — and a service account that holds one is the usual route from a web/app foothold to SYSTEM. This page covers which privileges matter and the "Potato" family that turns one of them into a SYSTEM shell. It builds on Windows Access Tokens & UAC.

The privileges that are really admin

Check your token with whoami /priv. Several privileges, if Enabled (or enable-able), are escalation primitives:

PrivilegeWhy it is dangerous
SeImpersonatePrivilegeImpersonate a token you can make connect to you — the key to every Potato (common on service accounts, IIS, MSSQL).
SeAssignPrimaryTokenPrivilegeAssign a primary token to a new process — the same Potato primitive by another route.
SeDebugPrivilegeOpen any process — read LSASS, inject into a SYSTEM process.
SeBackupPrivilegeRead any file ignoring the DACL — copy SAM/SYSTEM/NTDS.dit.
SeRestorePrivilegeWrite any file — overwrite a service binary or a DLL a SYSTEM process loads.
SeTakeOwnershipPrivilegeTake ownership of any object, then grant yourself access.
SeLoadDriverPrivilegeLoad a (vulnerable) driver → kernel code execution (BYOVD).

The Potato pattern

The Potato attacks all exploit the same idea. A service account holding SeImpersonate cannot directly become SYSTEM — but it can impersonate a token it is handed. The trick is to coerce a SYSTEM process into authenticating to a listener you control (via a local RPC/COM or named-pipe primitive), capture or receive that SYSTEM token, and impersonate it to spawn a process as SYSTEM. No password, no memory corruption — just abusing trusted local IPC plus the impersonation privilege the account already has.

The whole family reduces to: force SYSTEM to talk to me → impersonate the SYSTEM token I receive → run my command as SYSTEM. Which Potato you use depends only on which coercion primitive the Windows version and patch level leaves open.

The family — which one, when

ToolPrimitive / when it applies
PrintSpooferAbuses the Print Spooler's named pipe (SpoolSS) — the go-to on modern Windows 10/Server 2016–2019 where Spooler is up.
RoguePotatoRedirects the OXID resolver over a fake RPC to coerce SYSTEM — works where the DCOM trick was patched.
JuicyPotato / JuicyPotatoNGThe original DCOM/BITS CLSID abuse — effective on older builds (pre-Server 2019) that still allow it.
GodPotato / SweetPotato / EfsPotatoNewer, broad coverage across current builds using RPC/EFSRPC coercion — the current default when Spooler is off.
 
# confirm the privilege
whoami /priv | findstr SeImpersonate
# then run a Potato appropriate to the build (example shapes)
PrintSpoofer.exe -i -c cmd
GodPotato.exe -cmd "cmd /c whoami"   # should return nt authority\system

Token abuse beyond Potatoes

  • SeBackup/SeRestore → read the SAM & SYSTEM hives (or NTDS.dit on a DC) and extract hashes offline.
  • SeDebug → dump LSASS (see Windows Credential Storage) or inject into a SYSTEM process.
  • SeLoadDriver → load a known-vulnerable signed driver and execute in the kernel (BYOVD) — also a path to disabling EDR.
  • Token theft / impersonation → already-SYSTEM/admin? Duplicate another logged-on user's token to act as them, including for lateral movement.

Detection & hardening

  • Grant SeImpersonate/SeAssignPrimaryToken only where genuinely needed; audit service-account privileges.
  • Disable the Print Spooler on servers that do not print (kills PrintSpoofer and PrintNightmare at once).
  • Alert on a service/IIS/SQL account spawning cmd/powershell as SYSTEM, and on named-pipe impersonation patterns (Sysmon 17/18 — see Logging).
  • Block vulnerable drivers (Microsoft's blocklist / WDAC) to close SeLoadDriver and BYOVD.
