Kubernetes & Container Attacks

2026-10-09 · 11 min read

Containers and Kubernetes add their own layer to the attack surface: a compromised application now sits inside a pod, on a node, in a cluster, in a cloud account — and each boundary is one an attacker tries to cross. The recurring goals are escape the container to the node, abuse Kubernetes RBAC and service-account tokens, and pivot from the cluster into the cloud.

From a pod: what you start with

A web app RCE usually lands you in a container. First checks: 

# am I in a container? what can I reach?
cat /proc/1/cgroup; ls -la /.dockerenv
# the mounted service-account token -> talk to the Kubernetes API
cat /run/secrets/kubernetes.io/serviceaccount/token
env | grep -i kube     # API server address, and sometimes cloud creds

Container escape

WeaknessEscape
Privileged container--privileged or dangerous capabilities (CAP_SYS_ADMIN) let you access host devices and mount the host filesystem.
Host mountsA pod that bind-mounts the host disk, /var/run/docker.sock, or host paths — read/write the host directly.
hostPID / hostNetworkShared host namespaces expose host processes and the node network.
Kernel / runtime CVEsrunc/containerd escapes and kernel bugs that break isolation.

The classic path: a container with the Docker socket mounted can start a new container that mounts / from the host and chroot into it — instant node root.

Kubernetes RBAC & service accounts

Every pod gets a service-account token that authenticates to the API server with that account's RBAC rights. Over-permissioned service accounts are the Kubernetes equivalent of an over-privileged IAM role:

  • create pods / exec — schedule a privileged pod or exec into others; a path to any node.
  • get/list secrets — read every secret in the namespace (database creds, cloud keys, other tokens).
  • create on roles/bindings — grant yourself cluster-admin.
  • Access to the kubelet API or an exposed etcd — read all cluster state and secrets directly.
The escalation graph is: pod → service-account rights → cluster-admin or a node → every workload. Tools like kube-hunter and the kubectl auth can-i --list check map what a token can do — the first thing to run with any token.

Cluster → cloud pivot

Managed clusters (EKS/AKS/GKE) tie node and pod identities to cloud IAM. From a node you can often reach the cloud metadata endpoint and assume the node's cloud role (see AWS and Azure), turning a cluster compromise into a cloud-account compromise. IRSA/workload-identity bindings are the intended control — and the thing to abuse when loosely scoped.

Detection & hardening

  • Pod Security Standards / admission control to forbid privileged pods, host mounts and host namespaces; drop capabilities by default.
  • Least-privilege RBAC; disable auto-mount of service-account tokens where not needed; network policies between namespaces.
  • Lock down the kubelet and etcd; never expose them; restrict metadata access from pods (IMDSv2, network policy).
  • Runtime security (Falco) and audit logging of the API server for exec, secret reads, and RBAC changes — ship to the SIEM (Logging).
