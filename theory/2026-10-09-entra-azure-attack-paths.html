Entra ID & Azure Attack Paths

2026-10-09 · 12 min read

In cloud-first organisations the crown jewels sit in Entra ID (Azure AD) and Microsoft 365, not an on-prem datacentre. The attack surface is identity and tokens rather than hosts and hashes, and the hybrid link back to on-prem Active Directory means compromise can flow in both directions. This page maps the common Entra/Azure attack paths.

The identity model, briefly

  • Entra ID roles (e.g. Global Administrator) govern the directory and M365; Azure RBAC roles (Owner, Contributor) govern resources in subscriptions. They are separate — and the bridge between them is a known escalation.
  • Tokens are the currency: access tokens, refresh tokens, and the Primary Refresh Token (PRT) that a joined device holds. Steal the token and you are the user — MFA already satisfied.
  • Service principals & managed identities are non-human identities with their own, often over-broad, permissions.

Escalating in the cloud

  • Over-privileged roles — find an account or app with Global Admin, Privileged Role Administrator, or Application Administrator and ride it; Application Admin can add credentials to a privileged service principal.
  • Service principal / app abuse — add a secret to an app that holds high Graph permissions, then act as it.
  • Managed identity abuse — from a compromised VM/function, request a token for its managed identity from the metadata endpoint and use its RBAC rights.
  • RBAC → directory bridge — a user with User Access Administrator / Owner can elevate themselves over the root management group and reach resources broadly; the Global Admin "elevate access" toggle grants Azure RBAC over everything.

The hybrid bridge — both directions

Most enterprises sync on-prem AD to Entra with Entra Connect. That server is a prime target in either direction:

  • On-prem → cloud — the Connect server holds credentials able to write to the cloud; compromising it (or the AD Connect account) can mint or reset cloud identities. PHS exposes synced password material; PTA agents can be backdoored to capture every cloud logon; Seamless SSO has its own abuse (the AZUREADSSOACC account is a Silver-Ticket-like target).
  • Cloud → on-prem — Intune/Endpoint-manager and cloud-management of hybrid-joined devices can push scripts to on-prem machines; a cloud admin can thereby run code on-prem.
The hybrid link collapses the old perimeter: owning Entra can lead to on-prem code execution, and owning on-prem (via the Connect server) can lead to the cloud tenant. Treat the two as one blast radius.

Tooling

  • AzureHound — graph the tenant like BloodHound does AD, to find role and ownership paths.
  • ROADtools / AADInternals — enumerate and manipulate Entra, abuse PHS/PTA/Seamless SSO, and work with tokens.
  • Microsoft Graph & Azure CLI — the legitimate APIs, which are also the attacker's primary interface.

Detection & hardening

  • Minimise Global Admins, use Privileged Identity Management (just-in-time roles), and enforce phishing-resistant MFA (FIDO2) for admins.
  • Monitor sign-in logs and the audit log for risky sign-ins, consent grants, new app credentials, and role changes; alert on impossible-travel and legacy-auth.
  • Harden the Entra Connect server as a Tier-0 asset; monitor PTA agents and the Seamless SSO account.
  • Conditional Access to constrain where and how tokens can be used; token-protection/binding to limit replay.
